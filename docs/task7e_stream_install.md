# Task 7E: 区画完成と地形再描画の分離

2026-10-29。Godot 4.7.2 / Compatibility、RTX 3060、1280×720。計測と画像は `builds/qa/stream_install/`。

## 変更

前回中断時の5ファイルの実装を引き継いだ。DrawChunkの版管理・計時は既に入り、未完成の宣言はなかった。7E初回では全件ソートを除去したが、全件走査とidle判定の誤りが残っていた。Claudeの差分レビューと通常ループの計測で、全25区画の完成後も画面外の待ち行列が1179個のまま400フレーム停止する問題が判明した。物理を止めた排出検査では検出できていなかったため、7E-fixで修正し、通常ループの回帰検査を加えた。

- `streamed_terrain.gd`: 衝突・セル・行衝突・薄い足場・接続マスクが揃えば地形の取り込みを完了する。区画管理側で敵・ハート・報酬・商人・ボス・背景を取り込み終えてからloadedへ公開する。画面外の再描画を待たない。
- `world_terrain.gd`: DrawChunkの変更版・提出版・描画済み版を保持し、`_draw`のCPU時間を計測する。新しいフックで破壊・復元・設置壁の追加・除去・点滅を共通の再描画経路へ送る。静的地形と練習場は従来どおり即時要求する。
- 新規チャンクはツリー追加前に隠す。Godotの初回自動描画による約430チャンクの一括描画を避け、視界を先に表示する。整数チャンクキーは原点移動で変わらない。解放時は該当キーを待ち行列からも削除する。
- `world_backdrop.gd`: 区画完成フレームに背景48チャンクの初回描画が集中していたため、背景もツリー追加前に隠し、余白込みの視界に入る分を必ず表示する。画面外の背景は視界へ入るまで描画命令を作らない。背景のデータとノードは区画完成時に揃える。整数キー・描画済みフラグを保持し、原点移動後の背景も自動検査する。
- `main.gd`: カメラの次位置計算を共通化し、現在と次の視界を統合して余白を付ける。物理の先頭で必須描画を提出し、周囲8区画・視界の完成・提出版の一致を保留条件に使う。世界の物理による変更後もidleの末尾で再確認する。保留中もこのidle処理は動く。
- mainの`_process`は1個。`process_physics_priority=-100`を維持し、追加したidleだけ`process_priority=1000`。既存のHUD更新・入力・地図・矢印の処理は移さない。`streaming_enabled=false`の静的検査・練習場では新しい描画サービスを呼ばない。
- 待ち行列は重複を辞書で集約し、8×6チャンク（1区画相当）の束にも索引を持つ。移動方向の3秒先の点に中心が近い束を選び、その束内で最も近いキーを選ぶ近似順。25区画・約1200キーでも調べるのは最大25束と48キーで、全件走査を行わない。追加・提出・解放時に両辞書を更新し、原点移動では整数キーを保つ。視界内の必須更新数は制限しない。
- `sector_stream.service_did_work`を各`service()`の冒頭でfalseにし、生成結果の取得・地形構築・敵等の取り込み・解放・増員ジョブの取得/起動・増員候補の処理をした場合だけtrueにする。増員候補の延期や棄却も仕事に含む。空のポーリングで計時値が正になっても仕事とは判定しない。
- mainは描画までの全物理コールバックで仕事フラグをOR、サービス時間を合計し、idleの提出後に両方をリセットする。物理が1描画フレームに2回動き、最初だけ仕事をした場合もidle例外を使わない。開始し直す際もリセットする。
- 合計サービス時間を1.5ms枠から差し引き、必須更新と任意更新の推定描画時間で追加提出を判定する。待ち行列自身の時間は`redraw_service_ms`に計測するが、提出を止める判定には加えない。描画の推定は実測の指数移動平均（係数0.1、初期1.2ms）。`redraw_estimated_ms`で推定描画と区別する。通常の画面計測には管理時間・実描画・GPU待ちを含む。
- 1チャンクの`_draw`は分割できない。明示的な仕事フラグがfalseで必須更新もないフレームでは、推定コストが残り枠を超えても1個許可する。枠の浮動小数点比較でidleを判定しない。時間枠は単独チャンクにも適用できる厳密な上限ではない。

完成ジョブの生成枠の管理・生成アルゴリズム・ワーカー数は変更しない。描画待ちの除去で実時間の保留を解消できたため、完了ジョブの別キューは追加しなかった。

## 固定fpsの保留数の解釈

初回7Eで158→272に増えた実行には保留区間の実時間を記録していなかったため、その114フレーム増加の原因を確定できない。記録済みの物理平均は1.347→1.359ms、ワーカー生成平均104.329→108.304msで、これだけでは説明できない。

追加の`fixed_wall_probe.gd`を同一内容で7E前・7E初回・修正後の写しへ置き、同じウォームアップと900固定fpsフレームを画面なし・待ち時間なしで単独実行した。

| 条件 | 保留数 | 保留したフレーム区間の実時間合計 | 全900フレームの実時間 | 1フレーム平均 / 最大 |
|---|---:|---:|---:|---:|
| 7E前 | 157 | 407.428ms | 4357.187ms | 4.841 / 444.442ms |
| 7E初回（修正前） | 93 | 89.853ms | 3396.806ms | 3.774 / 32.350ms |
| 7E-fix | 68 | 107.575ms | 3668.444ms | 4.076 / 33.672ms |

これは各`physics_frame`〜`process_frame`の間隔を観測した実時間で、GPU計測ではない。再実行では272個の増加自体を再現せず、保留数93→68でも保留区間合計は増えた。固定fpsのフレーム数が待った実時間の長さを表さないことが分かる。初回一括描画を外すことで最大フレームと全ループ時間が短縮し、ワーカーが生成する同じ実時間にメインがより多くの固定fpsフレームを進め得る、というのが158→272の有力な説明だが、当該実行の時間記録がないため推測に留める。実時間歩行の保留0と区別する。

今回の全テストに含めた単独の`streaming_performance.gd`は21項目成功、保留55フレーム、物理平均1.628ms、ワーカー生成平均105.385ms（`fix-full-tests/fixed-performance.json`）。上の追加プローブとは別の実行なので、68との一致は仮定しない。

## 検査

`tests/stream_redraw_test.gd`を追加し、`test.cmd`に登録した。

- mainの保留判定直後、世界を進める各物理フレームで余白込み視界の提出版を検査する。idle末尾でも未処理がないことを検査する。通常描画では`frame_post_draw`後に描画済み版も照合する。
- 物理監査はmainのカメラ更新後に走るため、更新後の実視界に最大速度・天井補正・64pxの余白を付けて調べる。ここでさらに次のカメラ位置を再予測すると、保留判定から2回先を調べることになるため、それはidle末尾で確認する。地形と背景の両方を検査する。
- 実際の歩行・最大速度の落下・空中ダッシュが発生したことを検査する。床の掘削、ブロック破壊・復元、支持面への設置壁・点滅・除去、区画の追加・解放、原点移動を含める。
- わざと未準備の場所へ試験用に移動し、保留中はゲーム時刻が増えず、取り込みと再描画が進んで復帰することを検査する。製品の移動仕様にワープを追加するものではない。
- 再描画要求後の提出を止めた負例では、同じ`view_is_current`判定がfalseになる。次のフレームで修復できることも照合する。
- 描画コスト推定を意図的に枠の3倍にしても待ち行列が空になること、隠れたチャンク・解放済みキー・古い提出版が残らないことを検査する。
- 7E-fixでは物理を止めずに全25区画の完成を待ち、800個以上の待ち行列から実測推定値と毎フレーム枠の3倍に上書きする条件を各122フレーム検査する。mainのidle後に記録し、取り込み・ジョブのない2フレームにつき1個以上減ること、管理時間の平均0.5ms未満を確認する。2回の物理コールバックの最初だけに仕事を作り、仕事フラグのORと時間の合計も照合する。
- JSON出力とcontrols_pathの親を、ゲームを作る前に`DirAccess.make_dir_recursive_absolute`で作成する。設定ファイルがない場合は`ConfigFile.load`の失敗から既定値を使う既存経路で処理する。

初回の凍結検査は既に空のキューとの比較で失敗したため、明示的にdirtyにしてから進行を見るよう修正した。ただし物理を止めた検査のため、通常ループでidle例外が働かない点を見逃した。7E-fixの最終版の新検査を修正前の写しで実行すると、121フレームで実測推定値の減少23個、枠の3倍では0個となり、両条件の進行率で失敗した（終了コード1、`fix-negative-final.log`）。実測推定値での全停止までは同じ条件で再現しなかったが、必要な進行率を満たさないことは再現した。

`streaming_performance.gd`には16.7ms超のフレームの番号、取り込み・物理・再描画の管理時間と推定描画時間を追加した。途中の最大25.554msのフレーム89では地形描画の推定追加0ms、待ち行列0.070msで、取り込み3.997ms・物理全体9.469msだった。区画完了ごとの背景初回描画を分離する判断に使った。途中結果は`intermediate-selected/`に保存する。
